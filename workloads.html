ORYVAEL Workloads

Containers,
evolved.

Containers made software portable. ORYVAEL Workloads extend that idea by making authority portable too: artifact identity, principal identity, capabilities, resource budgets, object visibility and evidence become one native runtime contract.

Natural evolution

Keep the container experience.
Replace ambient authority.

ORYVAEL does not need to reproduce Docker Engine or Linux namespaces as its native substrate. It can preserve the useful philosophy — reproducible artifacts, registries, fast lifecycle and isolation — while rebuilding execution around ORYVAEL primitives.

CLASSIC CONTAINER MODEL

Constrain a Linux process.

  • image + filesystem layers
  • namespaces
  • cgroups
  • seccomp / LSM defense in depth
  • UID/GID/root compatibility semantics
  • Linux kernel runtime boundary
ORYVAEL WORKLOAD MODEL

Instantiate explicit authority.

  • verified immutable artifact
  • workload principal
  • kernel-owned capability handles
  • resource budget
  • object namespace
  • volumes + bounded secret operations
  • audit and evidence by construction

The intended shift is not cosmetic.

Isolation stops being the whole security story. Authority becomes a first-class runtime object.

Native invariants

No privileged mode.
No native root escape hatch.

A workload can only operate on objects represented by capabilities instantiated for its principal. Compatibility identities may exist later, but they cannot widen native authority.

01

Deny by default

Network and object access begin denied. Missing authority is not inferred.

02

No wildcard authority

The manifest contract rejects broad * capability requests.

03

No self-grant

Workloads cannot request kernel, policy, root or capability-administration authority.

04

Secret operations

Signing or decryption handles are preferred to placing raw private keys inside the workload.

The artifact is not the authority.

An image can contain code and metadata. It does not get to decide what the machine grants it.

  • artifact digest identifies executable content;
  • manifest describes requested runtime authority;
  • policy decides what may actually be granted;
  • kernel handles enforce the decision;
  • audit records the lifecycle and use of authority.

OCI without runc dependency

Reuse distribution.
Own execution.

OCI is valuable as a content-addressed distribution ecosystem. ORYVAEL can consume registry manifests, layers, signatures, attestations and SBOMs without making Linux container semantics its native runtime.

REGISTRY

Pull / push

Reuse mature content distribution and caching infrastructure.

DIGEST

Immutable identity

Bind execution and evidence to exact artifact bytes rather than mutable tags alone.

PROVENANCE

SBOM + attestations

Carry build evidence and publisher identity alongside the artifact.

POLICY

Independent authority

Being downloadable from a registry never implies permission to execute with requested rights.

The manifest schema, Rust model, semantic validator and workload-check command exist now. Native pull/run/ps/logs/stop/rm, artifact storage, workload lifecycle and OCI registry execution do not yet exist in the bare-metal image.

Implementation path

Build on Phase 2.
Do not invent a second security model.

The workload runtime starts after the kernel already has real processes, object handles, capabilities, identities, resource accounting and audit.

01

Artifact store

Content-addressed immutable objects and verified local cache.

02

Workload manager

Create, start, stop, replace and destroy attributed instances.

03

Runtime objects

Resource budgets, filesystem views, socket handles, volumes and secrets.

04

OCI bridge

Registry client, layers, signatures, provenance and native platform artifacts.

05

MicroVM backend

Stronger boundary for hostile code and Linux compatibility workloads.
